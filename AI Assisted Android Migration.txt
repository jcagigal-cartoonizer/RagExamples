AI-Assisted Android Migration from Views to Jetpack Compose
I developed this project as an internal proof of concept to explore how AI and RAG-based workflows can accelerate real-world software modernization tasks.

THE TASK

Migrate an existing Android application built with Jetpack Views to Jetpack Compose:

- Incrementally, one fragment at a time

- Preserving the existing navigation during the first phase

- Delivering a final version fully based on Compose UI and Compose Navigation

WHAT I DID

Because Views navigation and Compose navigation cannot coexist in the same architecture, I followed a two-step migration strategy aligned with Google’s recommended approach:

- First migrate all fragments to Compose keeping the same navigation. This can be achieved because Jetpack views can host composables, so it was a matter of replacing the old xml layouts with new fragments that just hosted the composable inside a ComposeView.

- Once the composables were validated and stable, I replaced the legacy navigation layer with Compose Navigation, completing the transition to a fully Compose-based app.

To support this process, I built a custom AI assistant was LangChain4j (similar to LangChain Python but written in Java) because I found it more flexible and also because, being pure Java, it lets you use the plethora of java tools and libraries. Amongst other things, it lets you easily integrate with Spring Boot, for instance. And of course use any database as input to the RAG process.

For the language model, I used OpenAI GPT-5.4-mini.

The assistant does the following:

- Load the relevant project files, including fragments, XML layouts, and navigation definitions

- Split the source code into manageable chunks and store them in a vector database for retrieval

- Use a Query Transformer to combine the user prompt with the project context

- Apply a Retrieval Augmentor to manage the RAG pipeline effectively

- Generate the updated code through an AI assistant powered by OpenAI

After generating the output, the assistant also used custom agent tools to post-process the results and create the corresponding files, including composables, UI state classes, UI events, and related components.

The AI-generated output still required some manual refinement, mainly to resolve inconsistencies and add missing imports. However, even with this final review step, the migration time per fragment — including the navigation update — was reduced by approximately 5x compared to a fully manual migration.

The final navigation conversion phase was handled by a second assistant, with no manual intervention required.

Testing was still necessary, as with any migration project, but that would also be required in a traditional manual approach.

CONCLUSION

Based on this experience, I can confidently say that this AI-assisted workflow can significantly accelerate Android modernization projects. For teams looking to migrate from Views to Compose, this approach can reduce delivery time substantially while preserving control over the codebase and migration quality.

In practice, this method allowed me to migrate an Android app from Views to Compose in about 5x less time than a manual approach.
