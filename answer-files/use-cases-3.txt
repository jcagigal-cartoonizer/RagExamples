QUESTION
How to add guardrails in RAG to limit the Ai model to access certain resources. For instance, forbid the connection with web that require authentication
ANSWER
To add guardrails in a RAG system, the key idea is:

**Don’t let the model decide what it can access.**  
Instead, enforce access rules in the **retrieval/orchestration layer** before any content is sent to the LLM.

If you want to **forbid connections to authenticated web resources**, the safest approach is to make the system **network-restricted by design** and only allow retrieval from approved sources.

---

## 1) Core principle: separate “reasoning” from “access”

A RAG pipeline usually has:

1. User query
2. Retrieval from sources
3. Context passed to LLM
4. Answer generation

Guardrails should be applied at step 2, not after the model has already fetched data.

### Good pattern
- The LLM can only see documents returned by an approved retriever
- The retriever can only query approved indexes/connectors
- Any external web access is blocked unless explicitly allowed

### Bad pattern
- Letting the LLM call arbitrary tools or browse the web freely
- Relying on prompt instructions like “do not access authenticated sites”
- Filtering the answer after the fact only

---

## 2) Best ways to block authenticated web access

### A. Use an allowlist of sources
Only permit retrieval from:
- Internal document stores
- Approved public websites
- Specific APIs
- Pre-indexed corpora

Block everything else.

Example policy:
- Allowed: `sharepoint.company.com`, `confluence.company.com`, `docs.vendor.com/public`
- Forbidden: any site requiring login, cookies, SSO, or bearer tokens unless explicitly approved

---

### B. Disable general web browsing tools
If your agent framework supports tools, do not expose a generic browser tool.

Instead:
- Provide only specific retrieval tools
- Remove “open URL”, “search web”, or “fetch page” tools
- Use a controlled connector that only accesses approved domains

This is one of the most effective guardrails.

---

### C. Enforce network-level restrictions
Even if the model tries to access something, the infrastructure should prevent it.

Use:
- Outbound firewall rules
- VPC egress controls
- Proxy allowlists
- DNS filtering
- Private endpoints for internal systems

This ensures the app cannot reach authenticated or unapproved sites at all.

---

### D. Use authenticated connectors only where needed
If some resources require auth, don’t let the model authenticate dynamically.

Instead:
- Use service accounts with scoped permissions
- Preconfigure connectors
- Restrict tokens to specific domains and paths
- Rotate credentials and log access

If a resource is not approved, do not provide credentials for it.

---

### E. Add source classification and policy checks
Tag each source with metadata such as:
- `public`
- `internal`
- `restricted`
- `requires_auth`
- `pii`
- `regulated`

Then apply policy rules before retrieval:
- If `requires_auth = true` and not approved, block
- If domain not in allowlist, block
- If user role lacks permission, block

---

## 3) Recommended architecture

A secure enterprise RAG setup often looks like this:

**User query**  
→ **Policy engine** checks user permissions and allowed sources  
→ **Retriever** searches only approved indexes  
→ **Reranker** ranks results  
→ **Context filter** removes disallowed chunks  
→ **LLM** generates answer from approved context only

### Important
The LLM should never directly fetch web pages.  
It should only receive retrieved text from the controlled pipeline.

---

## 4) Practical guardrails to implement

### Access control guardrails
- RBAC / ABAC on documents and indexes
- Per-user or per-group permissions
- Row-level or document-level security
- Tenant isolation

### Retrieval guardrails
- Domain allowlist
- Path allowlist
- Metadata filters
- Query-time policy checks
- Max source count and source type restrictions

### Tool guardrails
- No arbitrary browser tool
- No shell/network tools
- No URL fetch unless validated
- No auth-capable connectors unless explicitly approved

### Output guardrails
- Require citations from approved sources
- Refuse to answer if no approved source is found
- Mark uncertainty clearly
- Block leakage of restricted content

---

## 5) Example policy logic

Here is a simple policy idea:

```text
Allow retrieval if:
- source.domain is in allowlist
- source.requires_auth is false
- user.role is permitted for source.classification
- source is in approved index
```

Example deny rules:
```text
Deny if:
- URL domain not in allowlist
- URL contains login/auth endpoints
- source requires interactive authentication
- source is marked restricted and user lacks clearance
```

---

## 6) Example implementation approach

### Option 1: Pre-index only approved content
This is the safest and simplest.

- Crawl only approved public pages
- Ingest internal docs from approved repositories
- Index them in a vector database
- Query only the index

No live web access at runtime.

### Option 2: Controlled live retrieval
If you must fetch live content:
- Use a proxy service
- Validate URL against allowlist
- Block auth-required pages
- Strip cookies and credentials
- Log every request
- Cache approved content if needed

## 7) Example pseudo-code

```python
ALLOWED_DOMAINS = {"docs.company.com", "support.vendor.com"}

def is_allowed_url(url):
    domain = extract_domain(url)
    if domain not in ALLOWED_DOMAINS:
        return False
    if requires_auth(url):
        return False
    return True

def retrieve(url, user):
    if not is_allowed_url(url):
        raise PermissionError("Access denied by policy")
    return fetch_public_content(url)
```

For RAG retrieval:

```python
def rag_retrieve(query, user):
    candidates = search_index(query)
    approved = []
    for doc in candidates:
        if doc.domain in ALLOWED_DOMAINS and not doc.requires_auth:
            if user_has_access(user, doc):
                approved.append(doc)
    return rerank(approved)
```

## 8) If you use agent frameworks

For frameworks like LangChain, LlamaIndex, Semantic Kernel, or custom agents:

- Register only approved tools
- Wrap tools with policy checks
- Validate every tool call
- Deny unknown domains
- Log tool usage
- Add a “human approval” step for sensitive actions

Do not rely on the prompt alone.

---

## 9) Strongest security pattern

If your requirement is specifically:

> “forbid the connection with web that require authentication”

Then the strongest pattern is:

1. **No direct web browsing by the LLM**
2. **Only pre-approved connectors**
3. **Network egress allowlist**
4. **No credentials for unapproved sites**
5. **Policy engine before retrieval**
6. **Audit logs for every access**

That combination gives you real enforcement, not just prompt-based behavior.

---

## 10) Short answer

To add guardrails in RAG:
- Put access control in the **retrieval layer**
- Use **allowlists** for domains/resources
- Block **authenticated web access** at the **network and connector level**
- Only expose **approved tools** to the model
- Enforce **RBAC/ABAC** and metadata-based filtering
- Require **citations from approved sources only**
